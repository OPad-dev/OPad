## 0. Verdict

The design is strong: latency isolation on the firmware side, NVS writes held back during play, ownership, signed updates, careful sync. Most tests pass. What stands between the repo and a release is not the architecture. It is five groups of work:

1. **Release engineering.** Builds only work on the author's machine. CI is red. The rename to `opad` broke flashing and updates. Packages miss tools they need.
2. **A few real firmware bugs.** Keys can go dead after pin detection. Frames can be truncated. Release firmware is built at `-Og`.
3. **Linux integration.** Nothing autostarts from deb/rpm, the AppImage is incomplete, and tosu may lack ptrace permission.
4. **Open-source compliance paperwork.** Third-party notices for binaries, tosu corresponding source, and a clear status for the GIF.
5. **Hardware/firmware alignment.** The PCBs use different pins than the firmware defaults, the HE module has no firmware, and the case has no PCB mounts.

### 1.2 P0: the easter-egg GIF (kept by decision)

`firmware/main/ui/easter_egg_gif.h` embeds `freaky_67_14f.gif` (15 656 bytes, 14 frames). Its author and license are unknown. You decided to keep it, and this guide doesn't reopen that decision. But it has one consequence you should plan around: **while an unlicensed third-party file is in the repo and in every firmware image, the project cannot truthfully say "100% open source" or "everything is MIT".** pid.codes reviewers and a buyer's legal check would both flag it.

Ways to keep the GIF and still reach a clean state, from best to acceptable:

1. **Get a license for it.** Find the original creator (reverse image search on the first frame; the file name suggests a meme or sticker source) and ask for permission under an open license (CC BY 4.0 or CC0 is simplest). Then add `firmware/main/ui/EASTER_EGG_GIF_LICENSE.txt` with the author, source URL and license, and list it in the README's third-party section. This is the only option that makes the GIF itself open source.
2. **Until then, label it honestly.** Add an SPDX header to `easter_egg_gif.h` that doesn't claim MIT (e.g. `// SPDX-License-Identifier: LicenseRef-Unknown-ThirdParty`). Mention it in the README license section as the single known exception. Make sure `reuse lint` (§1.6) lists it as the only non-compliant file. At least then the claim "everything else is open source" is true and checkable.
3. **Optional safety valve.** Keep the original artwork from commit `9193acc` (which you reverted) behind a build option, e.g. `CONFIG_OPAD_EASTER_EGG_ORIGINAL_ART`. If a pid.codes reviewer or a sale requires it, you can switch the shipped image without touching code. The GIF stays the default.

## 2. Firmware

### 2.1 P1: pin detection disables both keys when it finds nothing

`keypad_detect_pressed_pin` (`firmware/main/input/keypad.c:432-495`):
1. Reconfigures **every** scan pin, including the two active key pins (`14` and `9` are in `SCAN_PINS`), with `intr_type = GPIO_INTR_DISABLE` (lines 441-456).
2. At the end calls `board_keys_set_gpio(cfg.key1_gpio, cfg.key2_gpio)` to restore them (line 492).
3. But `board_keys_set_gpio` returns early when the pins equal the current ones (`boards/.../board.c:22-24`), which is exactly the case here. The interrupts are never turned back on.

**User impact:** the user opens Settings → Keys → "detect pin", and the detection times out or picks a pin that is already assigned. Both keys then stop sending HID reports until a reboot or a pin change. The ISR is the only path that sees edges; the task only resamples after a lockout.

**Fix:** at the end of detection, call `gpio_set_intr_type(pin, GPIO_INTR_ANYEDGE)` plus pull-up for the two active pins, or force the reconfigure (clear `s_key1_gpio`/`s_key2_gpio` first). Also exclude the two active pins from the `gpio_config` in step 1, since they already have pull-ups. Add a hardware checklist line: "detect pin → time out → keys still type".

### 2.2 P1: release firmware is compiled with `-Og` and assertions

`firmware/sdkconfig.defaults` doesn't set an optimization level, so every clean build (CI, release script, other developers) uses ESP-IDF's default `CONFIG_COMPILER_OPTIMIZATION_DEBUG` (`-Og`). The local `sdkconfig` shows exactly that. For a product whose first principle is "latency always wins", the shipped build should be `-O2`.

**Fix:** add `CONFIG_COMPILER_OPTIMIZATION_PERF=y` to `sdkconfig.defaults`. Keep assertions on at first (`ASSERTIONS_ENABLE`), since they are cheap and catch bugs. Then **re-run the Stage A-D latency measurements** in `docs/latency-testing.md` and record which optimization level each result used, because the current numbers were probably taken at `-Og`.

### 2.3 P1: CDC frames can be sent half-written

`usb_cdc_write` (`firmware/main/usb/usb_cdc.c:43-71`) writes as much as fits in the 512-byte TinyUSB TX FIFO. When the FIFO is full it flushes and **returns with the rest of the frame unsent**. `send_envelope` (`protocol/protocol.c:139-157`) only records a diag event. The host then gets a frame header promising N bytes, followed by the start of the *next* frame.

The host decoder (`opad-protocol/src/lib.rs:58-85`) has no way to recover. It reads the next 4 bytes as a length; any value up to 8188 is accepted, and it waits for that many bytes. Until they arrive, **every message from the pad is stuck**: HelloAck, status, counters, logs. On a busy link that means seconds; on a quiet one it can be minutes. The user sees "Connected" with frozen data.

**Fix, firmware side:** write a frame only if `tud_cdc_n_write_available(0) >= tx_len`; otherwise wait briefly (the task is on core 1 and can afford a few ms) or drop the **whole** frame.
**Fix, host side:** on any decode error, or if a partial frame sits unfinished for more than about 500 ms, clear `read_buf` and send Hello again. The firmware answers with a fresh HelloAck at a frame boundary.
**Protocol v2:** add a sync marker and a CRC (or COBS framing) so either side can resynchronise from any byte (§3).

### 2.4 P2: the `FREAKY67` trigger is matched inside binary frames

`is_easter_egg_command` (`usb_cdc.c:167-181`) searches every 256-byte read for the text anywhere, including in the middle of a protobuf frame. A song title, artist, mapper or player name containing `FREAKY67` (these come from tosu data the host forwards) triggers the animation. Worse, it calls `protocol_reset_rx()` and returns (`usb_cdc.c:198-203`), throwing away the rest of that read and the half-parsed frame, which desynchronises the stream as in §2.3.

The same file already explains, for `BOOTLOADER` (lines 143-150), why this must only be matched when the parser is idle and the read is exactly the command. **Fix:** apply the same rule: `protocol_rx_idle() && whole read == "FREAKY67"(\r\n)`. The in-band trigger (`DataValue.source == 67`, `protocol.c:570`) already covers the app's own use.

### 2.5 P2: any serial tool can drop the pad into download mode

`tud_cdc_line_state_cb` (`usb_cdc.c:269-275`) reboots into the ROM bootloader on an RTS falling edge while DTR is high. Serial monitors, Arduino-style port scanners and ModemManager-style probers make that pattern routinely. The pad then enumerates as `303a:1001` and stops typing until it's replugged or flashed. `FORCE_DOWNLOAD_BOOT` is an RTC register, so a power cycle clears it.

**Fix:** the host flasher already has a 1200-baud touch and the `BOOTLOADER` command (`opad-device/src/flash.rs`, `BOOT_TRIGGERS`). Remove the RTS-edge trigger, or require the exact esptool sequence (DTR low → RTS high → both released within ~100 ms) rather than any falling edge. Add `ENV{ID_MM_DEVICE_IGNORE}="1"` to the udev rule either way (companion doc §1.3).

### 2.6 P2: counter persistence window

`runtime.c:51-57` checkpoints lifetime counters every 5 minutes in IDLE, plus once after each cooldown. Presses in IDLE since the last checkpoint are lost if the pad is unplugged. Without tosu running, everything is IDLE, so up to 5 minutes of presses can be lost.

**Fix:** checkpoint 30-60 s after the last press when counts changed (a debounced write). NVS wear is not a concern at that rate: 3 small values, wear-levelled over a 24 KB partition. Also checkpoint on USB suspend (enable `CONFIG_TINYUSB_SUSPEND_CALLBACK`), which fires when the PC sleeps or shuts down.

### 2.7 P2: NVS format changes silently wipe counters and ownership

`device_config.c:113-119` and `counters.c:43-55` call `nvs_flash_erase()` on `ESP_ERR_NVS_NEW_VERSION_FOUND` / `NO_FREE_PAGES`. That erases **lifetime counters and the owner id**. It can happen after an ESP-IDF upgrade that changes the NVS format. A diag event is recorded, but the host doesn't act on it.

**Fix:** when the host sees `DIAG_EVENT_NVS_ERASED`, or a pad with generation 1 and zero counts whose device id it knows with higher counts, the GUI should offer "Restore counters from this PC" (the force-restore path already exists). Pin the ESP-IDF version (it is: `v5.5.2` in CI) and treat any IDF bump as needing an NVS-compatibility check.

### 2.9 P1: keyboard layouts

The pad sends HID **usage codes**, which are key *positions*, not letters. `0x1D` is "Z" on QWERTY, "W" on AZERTY and "Y" on QWERTZ. osu! binds by what the OS reports, so on a German or French layout the defaults don't match osu!'s default keys. The touch-retry key `0x35` (grave) is a different character on most non-US layouts. **Fix:** document this in the README, and have the GUI's key picker show the character for the host's current layout (or at least warn). No firmware change is needed.

## 4. Desktop daemon (`desktop/daemon`, `opad-device`, `opad-tosu`, `opad-storage`)

### 4.1 P1: device commands can be reordered or dropped

The main loop spawns **one tokio task per action** (`daemon/src/main.rs:437-510`, e.g. `SendDataUpdate`, `SendConfig`, `SendLayout`). Each ends in `DeviceManager::send_msg`, which does `try_send` on a 64-slot queue (`opad-device/src/lib.rs:328-336`). As a result:
- Two data updates spawned back to back can reach the queue in either order. The pad can show an **older** combo, pp or accuracy after a newer one.
- When the queue is full the result is `DeviceError::Busy`, which every call site discards (`let _ = …`). Data updates are **diffs** (`data_sync.take_changes`), so a dropped diff leaves a stale value on the pad until that source changes again.
- The device worker only drains the queue once per loop, and each loop can spend up to 100 ms in `read()` (`lib.rs:174, 243, 265`). Commands wait up to ~105 ms, which is visible on the HUD.

**Fix:** have a single owner task hold an ordered `mpsc` from the main loop, and `await` sends instead of spawning. Treat `Busy` for data updates as "resend the full snapshot next tick" (mark `data_sync` dirty). In the worker, use a 5-10 ms read timeout, or split reading and writing into two threads over `try_clone()` of the port.

### 4.2 P1: a panic leaves a half-dead daemon

There are 93 `lock().unwrap()` calls on `std::sync::Mutex` in non-test code (64 in `ipc_handlers.rs` alone). If any task panics while holding `daemon_state`, `storage` or `pending_ops`, the mutex is poisoned. From then on **every IPC request panics its own task**. The process keeps running, so systemd's `Restart=on-failure` never fires, and the GUI shows "online" but nothing works.

**Fix:** install a panic hook in `main` that logs and calls `std::process::exit(1)` (systemd or the GUI then restarts a clean daemon), or switch to `parking_lot::Mutex` (no poisoning). Doing both is best.

### 4.3 P1: lost device events

`tokio::select!` matches `Ok(dev_event) = device_rx.recv()` (`main.rs:286`). A `RecvError::Lagged` just disables the branch for that iteration, and the skipped events are gone. If a burst of `LogBatch`/`Counters` pushes a `Connected` or `Ownership` out of the 64-slot broadcast buffer, the daemon never learns the pad connected.

**Fix:** handle `Lagged` explicitly: log it and request a fresh HelloAck (send Hello again) so state is rebuilt from the pad. Raise the capacity to 256.

### 4.4 P2: counter sync fails while the user is pressing keys

`perform_sync` (`daemon/src/sync.rs:210-300`) computes `reconciled` once and retries the same numbers three times. If the user presses a key between the status read and the `CounterSync`, the pad's count is higher, the firmware correctly refuses ("non-monotonic", `counter_sync_rules.c:16`), and all three retries fail with the same stale numbers.

**Fix:** request status again and reconcile again before each retry. Firmware side: `counters_sync_from_host` reads counts and then overwrites them (`counters.c:148-157`). A press landing between those two lines (µs window, ISR on the other core) is lost. Apply the host value with a compare-and-swap, or add the delta pressed since the check.

## 6. CLI, flashing and updates

### 6.1 P0: artifact names don't match (rename fallout)

| Consumer | Looks for | Build produces |
|---|---|---|
| `opadctl flash <dir>` / `--full` (`cli/src/main.rs:743`) | `osupad-firmware.bin` | `opad-firmware.bin` |
| `opad-manifest` (`opad-update/src/bin/opad-manifest.rs:232,241,251`) | `osupad-firmware.bin`, `osupad-setup-*.exe`, `osupad-linux-x86_64-*.tar.gz` | `opad-firmware.bin`, `opad-setup.exe` (no version), `opad-linux-x86_64-<ver>.tar.gz` |
| `opad-manifest` default key (`opad-manifest.rs:361-374`) | `~/.config/osupad/opad-manifest.key` | `build_release.sh:105` checks `~/.config/opad/opad-manifest.key` |

The last row is new here. The release script checks one path and then runs a tool that reads another, so signing either fails or uses a key other than the one checked. **Fix:** one naming pass, plus a test that feeds `build_release.sh`'s output names through `app_artifact`/`firmware_artifact`. Pass `--secret-key` explicitly from the script.

### 6.2 P1: firmware update can corrupt a pad on the old partition layout

The update always writes the app to `0x20000` (`opad-device/src/flash.rs:26`) and never writes `otadata`. `firmware::blockers()` (`opad-update/src/firmware.rs:110-125`) checks connection, idle, storage, sync and consent, but **not the running slot**. Two cases break:
- **Pad on the pre-§U-3a single-app layout** (`running_partition` empty or `"factory"`, app at `0x10000`). Writing `0x20000` overwrites the middle of the running factory image. After reboot the bootloader loads a corrupt image and the pad stops working until a manual `--full` reflash.
- **Pad running `ota_1`** (possible once real OTA lands). `ota_0` is written, `otadata` still points at `ota_1`, and the pad boots the old version. The post-flash check then reports a mismatch.

**Fix:** add `Blocker::NeedsFullReflash` when `running_partition` is not `Some("ota_0")`, with a message pointing to `opadctl flash --full` / `docs/recovery.md`. When OTA is implemented, write the *inactive* slot plus `otadata`, and enable app rollback (§2.8).

### 6.3 Other CLI and update items

- P0: flashing needs `espflash`, which no package ships (companion doc §2.4).
- P1: the bootloader port choice can pick another ESP32 (companion doc §1.1).
- P1: AppImage updates want an `ArtifactKind::Binary` the manifest never produces (companion doc §3.2).
- P2: `opadctl setup` prints a relative `packaging/…` path (companion doc §3.5).
- P2: the deb/rpm update runs `pkexec apt-get install <file in the user's state dir>`. The file is hash-checked before, but a process running as the same user could swap it between the check and the root install. Copy it into a root-owned temp dir inside the pkexec'd command and check the hash there, or accept this and document it (an attacker who already runs as the user can wait for any sudo prompt anyway).

## 13. Security notes

These are not blockers, but should be written down in `SECURITY.md`.

- **Update signing:** minisign public key compiled in (`opad-update/src/verify.rs:34`); artifacts are SHA-256-checked against the signed manifest. Good. The private key lives on one laptop (`~/.config/…`). Keep an offline backup, decide who else can sign, and store it as a CI secret only if the release job signs.
- **IPC:** Unix socket in a 0700 dir with 0600 perms; Windows pipe with a user+SYSTEM DACL. Good.
- **tosu:** runs as the user and listens on `127.0.0.1:24050`. Anything local can read gameplay data; that's upstream behaviour. Document it.
- **Firmware:** no secure boot or flash encryption (fine for an open-source keyboard; say so, since some buyers ask). The `BOOTLOADER` CDC command means any local process that can open the port can reflash the pad; that's by design for a user-flashable device.
